TASK 8 — PR comparison across named periods

Feature IDs: F8
Depends on: Task 7 (Personal records); transitively Task 2 (User master data),
            Task 3 (Exercise & muscle-group master data), Task 4 (Unit conversion registry),
            Task 5 (Log workout entry)

User story
  As a coach, I want to compare a client's PRs between the current and previous period
  (week / month / year) so that I can see progress trends at a glance.

Acceptance criteria
  - When comparison is requested for a user, exercise, and granularity (week / month /
    year), the API compares the current period against the immediately preceding period of
    that granularity.
  - When the required timezone parameter (an IANA zone, e.g. "Asia/Ho_Chi_Minh") is
    supplied, the named-period boundaries (week / month / year, current vs previous) are
    computed in that timezone's local wall-clock and then resolved to UTC for querying, so
    "this month" reflects the caller's calendar rather than the server's. Omission of
    timezone -> 400 validation error.
  - When the periods are returned, the response includes a current and a previous block,
    each with its period start/end and the three PRs (max weight, max volume, best 1RM),
    each with its value and achieved-at date.
  - When both periods have data, a server-computed delta block gives, per PR metric, the
    absolute difference (current minus previous), the percent, and the direction.
  - The delta direction value set is: "up" (current > previous), "down" (current <
    previous), "same" (equal), "new" (previous is null but current is present -> null
    percent, no divide-by-zero), and "none" (current is null but previous is present).
  - When a period has no data, that period's PR fields are null (empty-but-not-an-error).
  - When the required unit parameter is supplied, all displayed weights are in that unit
    (delta computed on kg, converted for display only); omission -> 400.
  - When the userId is unknown, the API returns 404 USER_NOT_FOUND.
  - When the exerciseId is unknown, the API returns 404 EXERCISE_NOT_FOUND (consistent with
    the PR endpoint in Task 7).

Edge cases
  - Period boundaries are derived from the current time (via the injected time context) and
    the caller-supplied IANA timezone: local wall-clock period bounds are converted to UTC
    for querying.
  - No-data periods and null-previous / null-current deltas are handled via the direction
    value set above, never as errors.
  - Unknown user -> 404 USER_NOT_FOUND; unknown exercise -> 404 EXERCISE_NOT_FOUND.

Out of scope / assumptions
  - Only named relative periods (week/month/year current-vs-previous) this sprint — NOT
    arbitrary user-supplied date ranges.

Notes
  - Builds directly on the PR aggregation from Task 7 and the injected time context from
    Task 1.
